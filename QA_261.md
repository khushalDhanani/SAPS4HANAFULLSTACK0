# QA_261.md — manual QA script for the 261 app (run in a QA / sandbox S/4HANA client)

Purpose: exercise the **write** paths that are only mock-tested in CI (261 post, partial/sequential
posts, over-issue, multi-batch rejection, 262 reversal, WM delivery, timeouts) once against a real
client, and confirm the SAP outcome and the operator message. **Use a QA/sandbox client, not
production.** After every posting step read the document back in SAP (MB51 / MIGO display / COOIS) —
an HTTP 200 is **not** proof.

Pre-req users: a **WarehouseClerk** (post, scan), a **WarehouseManager/Admin** (reverse), a **Viewer**,
and a user **scoped to a different plant** (and one **scoped to two plants**). See *Test data
prerequisites* below for the data each scenario needs.

Fill **Result** (P = pass / F = fail / NT = not testable), **SAP doc no.** (every document created or
read back) and **Tester / date** for every row. Any divergence from "Expected" is a defect to log in
`WORKSTATUS.md` before release.

## Test data prerequisites
Create each, or mark the scenario **NT (Not testable)** with the reason — never skip silently.
- **Empty issue location (#7, 518006/3 shape):** a released order whose component reservation has `RESB-LGORT` = a **non-WM, empty** sloc (e.g. PT01) while the production supply area (`PRVBE` → `PVBE-LGORT`, e.g. CS01) holds stock. Reuse reservation **518006/3** if present, else build an order for a component whose supply-area sloc differs from the reservation sloc and has no stock in the reservation sloc.
- **Backflush component (#17):** a component with `RESB-RGEKZ` set (backflushing in the BOM/routing). If none exists in the QA client → **NT, "no backflush component configured"**.
- **Closed posting period (#14):** a material/period combination whose MM period is closed (MMRV/OB52). **Agree with Finance first** (see Cautions). If the client has no closed period → **NT**.
- **Two-batch component (#5):** a batch-managed component with stock in **≥2 batches** in the issue location/warehouse (two drums, two batches).
- **WM-managed sloc (#8):** a reservation whose issue sloc is in `T320` (warehouse-managed), so SAP turns the 261 into an outbound delivery.
- **Multi-plant / scoped users (#20, #21):** users with the `Plant` attribute set to one plant, two plants, and a different plant respectively.
- **Timeouts (#15, #16):** a way to force a network/SAP timeout (proxy throttle, firewall drop, or a very low `S4_HTTP_TIMEOUT_MS` in a QA app instance). If you cannot induce one → **NT, "cannot induce a timeout in this client"**.

## Cautions
- Use **dedicated test orders** for reversals (#9–#12, #16) — never reverse a document another team needs.
- **Record every SAP document number** (post and reversal) so the QA stock can be rebalanced afterwards.
- A **timed-out** post/reverse may have posted in SAP — always MB51-verify (#15/#16) before any retry; do **not** blindly retry.
- A **stuck attempt** (confirmed not-posted but still blocking a same-quantity retry with 409) can only be cleared today by a **DBA removing the `GoodsIssuePostingAttempt` row** (there is no self-service/admin reset — deferred). Note the reference and escalate. See *Runbook* below.
- **Agree the closed-period setup (#14) with Finance** before changing any period.

## Re-claim behaviour (what a retry does on its own)
A retry of the **same** posting no longer needs a DBA for the common cases — the attempt log now **re-claims** on its own when the prior attempt proves nothing posted:
- **Post:** a prior attempt in `rejected` (a definite SAP refusal) **or** `not_posted` (the recheck confirmed no document) is re-claimable → the operator can simply fix the cause and Post again (#24). A **live** attempt (`sending`/`unconfirmed`) or a **done** one (`posted`/`delivery_created`) still blocks with 409.
- **Reverse:** **only** `rejected` is re-claimable (#25). A reversal is **never** re-claimed on `not_posted`/`unconfirmed`, because the recheck looks a reversal up by our `RV…` key while SAP's `CancelItem` stamps the 262 with the *original 261's* reference — so a reversal that **did** post can be mislabelled `not_posted`, and auto-re-claiming it would risk a **double reversal**. A stuck reversal is cleared only via the Runbook after an MB51 check.
- Each re-claim **keeps the old row** and writes a new generation (the base reference with a trailing counter), so the audit trail is intact.

**Recheck timer (ops prerequisite):** the background recheck that ages `unconfirmed` → `not_posted` is started by `GoodsIssueService.init` in every runtime where `NODE_ENV` is **not** `test` and `GI_RECHECK_INTERVAL_MS` > 0 — so it **runs in the deployed QA/production app**. Confirm QA/prod is **not** started with `NODE_ENV=test` and the interval is not 0. Note the limitation: this shared timer confirms 201 outcomes; a **261/262-aware** SAP confirmation is **deferred** (WORKSTATUS) — for 261/262 always trust **MB51**, not the status.

## Runbook — clearing a stuck posting attempt
Use only when a retry is blocked by 409 and re-claim does **not** apply (a `sending`/`unconfirmed` row that the recheck has not yet aged, or a reversal left `not_posted`/`unconfirmed`).
1. **MB51 first (mandatory).** Look up the document in SAP (MB51 / MIGO display) using the material, plant, reservation and date. **Do not** touch the attempt row until you know whether SAP posted. If SAP **did** post → do **not** clear/retry (the goods issue / reversal is done); resolve the open qty from SAP, not from the app.
2. **Who may clear it.** Only a **DBA/basis operator** on an **approved change** (ticket) may delete the one `GoodsIssuePostingAttempt` row — identified by its `ReferenceDocument` (the `GI…`/`RV…` base + generation). No application user, clerk, or manager can clear it; there is no in-app reset (deferred).
3. **Log it.** Record in the change ticket: the `ReferenceDocument`, the MB51 finding (posted / not posted, with the SAP doc no. if any), who approved, who deleted, and when. Link the ticket in `WORKSTATUS.md`. Never delete a row without the MB51 finding attached.

## Release gate
**BLOCKERS — must pass to release:** #1 full post, #3 sequential partials, #4 double-click, #5 multi-batch,
#7 empty issue location, #9 reversal, #10 already-reversed, **#11 reverse after partial post** (restore is
SAP-side and only QA proves it), #12 reversal double-click, #18 Viewer-no-post, #19 clerk-no-reverse,
#20 plant scope, #21 multi-plant.
**MUST RUN — may be released with a documented limitation:** #14 closed period, #15 & #16 timeouts
(attempt auto-reconciliation for 262 is deferred — see WORKSTATUS), #17 backflush.
**MUST RUN — standard:** #2 partial, #6 over-issue, #8 WM delivery, #13 full-reversal-only check,
#22 concurrent users, #23 rugged-device, **#24 post-rejected re-claim, #25 reversal-rejected re-claim**.

Not covered here (by design): per-drum/storage-unit consumption (not expressible via the 261 API on this
LE-WM system — AUDIT_261 §F8 / Phase 7); the SAP master-data root cause of `RESB-LGORT=PT01` (functional
consultant: CDHDR/CDPOS, MRP area, OPJ8); a 261/262-aware re-check and a reset-attempt action (deferred —
see WORKSTATUS).
