# Business E2E Coverage Matrix

One row per UI5 route in `app/fiori-app/webapp/manifest.json`. `test/unit/tools/e2eCoverageMatrix.test.js` fails when a route is missing, a row names a route that no longer exists, a status is invalid, or a 🟢/🟡 row cites no existing E2E suite. Governance rule: `AGENTS.md` → *Change and test rules* → *Business E2E coverage*.

Statuses (updated 2026-10-26 ~15:40 IST from a READ-ONLY run of `npm run test:e2e` against the local server on :4004; no SAP write):

- **Browser E2E** — a Playwright suite under `test/e2e/` opens the route in a browser and checks: the router matched the route, a page title rendered, bound lists loaded without a load error, no error dialog/strip, no console errors, no HTTP >= 400, and no write request (Tier 0 write guard, `test/e2e/support/writeGuard.js`).
- **SAP round trip** — that suite performs the business action through the UI and reads the SAP result back (Browser → route → controller → CAP → S/4 → SAP result → UI). Requires a per-call written go.
- 🟢 suite exists and passed on the last recorded run · 🟡 partial or failing (say what) · 🔴 no E2E evidence · **N/A** not applicable (give the reason).

A 🔴 means no E2E evidence was found in the repository, not that the feature has no unit or integration tests.

## Running

`npm run test:e2e` runs the Tier A/B and authorization suites (`node test/e2e/runAllE2E.js`) against a running server (`npm start`); Tier C runs separately via `npm run test:e2e:sap`; it is not part of CI, which has no SAP connectivity. Tier A/B suites read SAP data through CAP (READ-ONLY) behind the write guard. Live SAP writes still require the user's written go per call (`AGENTS.md`).

Evidence: while `npm run test:e2e` runs, every browser session records a Playwright trace plus a final screenshot; for a failed suite they are kept in `test-results/e2e-evidence/<suite>/` (`session-N.png`, `session-N.zip`; last 8 sessions), for a passed suite they are discarded. Open a trace with `npx playwright show-trace <file>.zip`; the suite's entry in `test-results/e2e-summary.json` carries an `evidence` path. Registration: `test/unit/tools/e2eRunner.test.js` fails when a `*.e2e.js` suite is in neither `runAllE2E.js` nor `runSapRoundTrips.js`.

Contract check (request side): every browser session verifies each OData GET the UI sends to a CAP service (direct or inside a `$batch`) against that service's `$metadata` — entity set, `$select`, `$orderby`, `$filter` and `$expand` names must be declared (`test/e2e/support/contract.js`, unit test `test/unit/tools/e2eContract.test.js`). A violation is reported as a `CONTRACT:` console error and fails the suite. Not covered: response payload shape, `$filter` lambdas, `$apply`, `$search`, and actions' request bodies (only the Tier C suites check those).

Accessibility: `test/e2e/a11y/verifyA11yScreens.e2e.js` runs axe-core (WCAG 2.0/2.1 A and AA, serious/critical only) on the 21 parameterless routes; it fails only on violations absent from `test/e2e/a11y/baseline.json`. Refresh on purpose with `E2E_UPDATE_BASELINE=1`. Detail routes (path parameters) are not scanned. The baseline records existing findings, not fixes: `label-content-name-mismatch` on every screen, `aria-input-field-name` on the PO/inquiry/order create screens, Orders Due and the rack demo, and `aria-valid-attr-value` on Orders Due.

Performance: `test/e2e/performance/verifyScreenPerformance.e2e.js` times each parameterless route until the screen settles (median of 3 runs, 5 when recording) against `test/e2e/performance/baseline.json`; limit = baseline x 1.5 + 1000 ms. The limits are agent-chosen, not business-approved. Recorded 2026-10-27 on the local server with live SAP data: most screens 1.5-5 s, but `createPurchaseOrder` 25.6 s and `wmReservationEntryCreate` 23.0 s (cause UNKNOWN, not investigated; reported, not fixed).
