One row per UI5 route in `app/fiori-app/webapp/manifest.json`. `test/unit/tools/e2eCoverageMatrix.test.js` fails when a route is missing, a row names a route that no longer exists, a status is invalid, or a 🟢/🟡 row cites no existing E2E suite. Governance rule: `AGENTS.md` → *Change and test rules* → *Business E2E coverage*.

Browser status reflects recorded test runs only; the last full `npm run test:e2e` run recorded in `WORKSTATUS.md` passed 20/20 suites, and five affected suites were rerun after harness changes. No full suite rerun or live SAP round trip on the current HEAD is recorded. SAP statuses below describe dated evidence, not current system verification.

Statuses:

- **Browser E2E** — a Playwright suite under `test/e2e/` opens the route in a browser and checks: the router matched the route, a page title rendered, bound lists loaded without a load error (the MM, SD and WM list screens must also return at least one row, and their detail screens must open from the first row), no error dialog/strip, no console errors, no HTTP >= 400, and no write request (Tier 0 write guard, `test/e2e/support/writeGuard.js`).
- **SAP round trip** — that suite performs the business action through the UI and reads the SAP result back (Browser → route → controller → CAP → S/4 → SAP result → UI). Requires a per-call written go.
- 🟢 a cited suite exists and passed on its last recorded run · 🟡 partial or failing (say what) · 🔴 no E2E evidence · **N/A** not applicable (give the reason).

A 🔴 means no E2E evidence was found in the repository, not that the feature has no unit or integration tests.

## Running

`npm run test:e2e` runs the Tier A/B and authorization suites (`node test/e2e/runAllE2E.js`) against a running server (`npm start`); Tier C runs separately via `npm run test:e2e:sap`; it is not part of CI, which has no SAP connectivity. Tier A/B suites read SAP data through CAP (READ-ONLY) behind the write guard. Live SAP writes still require the user's written go per call (`AGENTS.md`).

CI PR gate: the `browser-e2e-sap-free` job runs `npm run test:e2e:sap-free` on every push and pull request, on `ubuntu-latest` with no environment or secrets. The runner starts its own `NODE_ENV=test` server with every SAP variable stripped (`test/e2e/support/isolatedServer.js`), proves SAP is unreachable, and runs only the suites marked `sapFree` in `test/e2e/runAllE2E.js` (Negative UI paths, Administration menu, Purchase Orders Ask AI panel, Write authorization, Quarantine labels, MIB labels). These prove UI handling, never SAP. SAP-reading screen and transaction suites remain in the manual job below.

CI manual: the `browser-e2e` job in `.github/workflows/ci.yml` runs the full `npm run test:e2e` (20 suites on 2026-11-14) on manual dispatch (`run_browser_e2e`, runner label `e2e_runner`) against a CAP server bound to the `dev-sandbox` environment secrets, after the RFC preflight, and uploads `test-results/e2e-summary.json`, `test-results/e2e-evidence/` and the CAP server log as the `browser-e2e-evidence` artifact. The runner must reach SAP and carry the SAP NW RFC SDK; the performance suite's limits were recorded on a developer machine and may not hold on a runner.

Evidence: while `npm run test:e2e` runs, every browser session records a Playwright trace plus a final screenshot; for a failed suite they are kept in `test-results/e2e-evidence/<suite>/` (`session-N.png`, `session-N.zip`; last 8 sessions), for a passed suite they are discarded. Open a trace with `npx playwright show-trace <file>.zip`; the suite's entry in `test-results/e2e-summary.json` carries an `evidence` path. Registration: `test/unit/tools/e2eRunner.test.js` fails when a `*.e2e.js` suite is in neither `runAllE2E.js` nor `runSapRoundTrips.js`.

Contract check (request side): every browser session verifies each OData GET the UI sends to a CAP service (direct or inside a `$batch`) against that service's `$metadata` — entity set, `$select`, `$orderby`, `$filter` and `$expand` names must be declared (`test/e2e/support/contract.js`, unit test `test/unit/tools/e2eContract.test.js`). A violation is reported as a `CONTRACT:` console error and fails the suite. Not covered: response payload shape, `$filter` lambdas, `$apply`, `$search`, and actions' request bodies (only the Tier C suites check those).
