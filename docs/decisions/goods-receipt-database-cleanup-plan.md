# Goods Receipt — database cleanup plan (requires explicit approval)

Date: 2026-11-21. Status: **PLAN ONLY. Nothing in this document has been executed.** No table was dropped, no migration was run, no HDI container was changed, and nothing was deployed.

Scope: the physical objects that the removed entity `saps4hana.wm.GoodsReceiptPostingAttempt` created in each database. The entity left the CAP model in commit `08a5f958` (branch `feature01`).

## 1. What exists and what the next deployment will do

Verified by compiling the model before the removal (`301434dd`) and after it (`npx cds compile db --to hana`):

| Design-time file (before) | Database object | In the model now | What the next HDI deployment does |
| --- | --- | --- | --- |
| `saps4hana.wm.GoodsReceiptPostingAttempt.hdbtable` | Column table `SAPS4HANA_WM_GOODSRECEIPTPOSTINGATTEMPT` | No | **Nothing.** The table and its rows stay in the container. |
| `saps4hana.wm.GoodsReceiptPostingAttempt.referenceDocument.hdbindex` | Unique index on `ReferenceDocument` | No | **Drops the index.** |

Why the two differ:

- The deployer is started with `node node_modules/@sap/hdi-deploy/deploy.js --use-hdb --parameter com.sap.hana.di.table/try_fast_table_migration=true` (`gen/db/package.json`, generated by `cds build`). There is no `--auto-undeploy`, and neither `mta.yaml` nor the three `mta/extensions/*/*.mtaext` files set `HDI_DEPLOY_OPTIONS`.
- `@sap/hdi-deploy` 5.7.0 documents that deleted files are *not* scheduled for undeployment unless they match the allowlist in `undeploy.json` (its README, section "Delta Deployment and Undeploy Allowlist").
- The generated `gen/db/undeploy.json` lists `src/gen/**/*.hdbview`, `*.hdbindex`, `*.hdbconstraint`, `*_drafts.hdbtable` and `*.hdbcalculationview`. The index file matches `*.hdbindex`; the table file matches nothing.

**Consequence to approve before any deployment of this branch:** the first deployment removes the unique index of the attempt table automatically. No row is lost, but it is a change to a deployed database object. Not verified by an actual deployment: this is derived from the build output and the deployer's documentation.

The seven administrator monitoring tables (`saps4hana.admin.*`) are still generated and are not affected.

## 3. Steps, each needing its own approval

Run per environment, lowest first. Stop at the first surprise.

1. **Read-only inventory (no approval for changes needed, but needs database access).**
   - Does the table exist: `SELECT TABLE_NAME FROM TABLES WHERE SCHEMA_NAME = CURRENT_SCHEMA AND TABLE_NAME = 'SAPS4HANA_WM_GOODSRECEIPTPOSTINGATTEMPT'`.
   - Row count and status split: `SELECT STATUS, COUNT(*) FROM SAPS4HANA_WM_GOODSRECEIPTPOSTINGATTEMPT GROUP BY STATUS`.
   - Open attempts: rows with `STATUS IN ('sending', 'unconfirmed')`, with `REFERENCEDOCUMENT`, `RESERVATIONNO` (delivery), `RESERVATIONITEM`, `ISSUEQTY`, `CREATEDAT`, `LASTERROR`.
   - Statements are **Not verified** against a HANA container; column names are the upper-case form of the CDS element names.
2. **Resolve open attempts against SAP (read-only in SAP).** For every open row, look up the 101 documents of the delivery item in SAP and record whether a receipt exists. An open attempt means the application did not know whether SAP posted; the business owner decides what that means now that the application no longer posts receipts.
3. **Export.** Export all rows (CSV or HANA export) with the SAP material document number and year, and store the export where audit evidence is kept. Record row count and checksum.
4. **Approve the index drop** that step 1 of the table above describes, or decide to deploy with an adjusted undeploy list instead.
5. **Drop the table — only with explicit written approval naming the environment.** Two ways, to be chosen then:
   - add `src/gen/saps4hana.wm.GoodsReceiptPostingAttempt.hdbtable` to an undeploy list (a project `db/undeploy.json`) for one deployment, then remove the entry again; or
   - undeploy that one file with the HDI deployer's `--undeploy` option.
   A plain SQL `DROP TABLE` inside an HDI container is not the supported route.
6. **Verify.** The table is gone, the seven `saps4hana.admin.*` tables are present, the application starts and `/health/ready` answers 200.

## 4. What must not happen

- No `--auto-undeploy` for this cleanup: it would schedule every deleted file, not only this table.
- No deletion or re-creation of the HDI container `saps4hana-db`: it also holds the user-lock and password-expiry monitoring state.
- No change to SAP material documents. Receipts posted earlier stay as they are.

## 5. Rollback

Before the drop, the table can be brought back into the model by restoring `db/wm/goods-receipt-attempt.cds` from commit `301434dd` and deploying. After the drop, the rows exist only in the export of step 3.
